**Réponses du LEAD (écrit, 24/09)** :
1. **Fichiers** : aucun processor n'écrit sur disque (pas de volume compose, pas de `VOLUME`, logs sur stdout).
2. **Variables** : il en manquait une **bloquante** — `SPACY_SERVICE_URL` (`graph-rag-llm-extractor-processor`, client `common_utils/grpc_clients/spacy_client.py`, défaut `graph-rag-spacy-service:50051`, valeur VM `graph-rag-spacy-service:50058`) → **`graph-rag-spacy-service` rejoint les services gRPC qui restent sur la VM**, joint par l'enabler `10.11.0.2:15058`. `EMBEDDING_SERVICE_URL` est **inutile** (client gRPC commenté) : `normalize-unite-retry` et `semantique-vigil` appellent l'embedding **en HTTP** (`EMBEDDING_API_URL`, `EMBEDDING_API_KEY`). Les autres variables ont un défaut correct (ports Prometheus, retries, TTL, files/exchanges, `LLM_TEMPERATURE`, `LLM_MAX_TOKENS`, `SERVICE_NAME`, `GRPC_TIMEOUT`).
   **LLM** : DeepSeek (`LLM_PROVIDER=deepseek` vérifié sur le conteneur prod), modèle par défaut `deepseek-v4-flash`, URL fixée dans le code → reporter `LLM_PROVIDER` et `DEEPSEEK_API_KEY` ; clés OpenAI/Gemini inutiles. ⚠️ **La clé API est imprimée en clair au démarrage** (`app/infrastructure/llm_client.py:36`) → F-HP-SEC-025.
3. **Double traitement** : le `CREATE` de l'ETL n'est pas atteint en prod (nœud sans `id` écarté plus haut ; **0 nœud sans id** dans le Neo4j prod : 33 213 `Produit`, 76 339 caractéristiques) ; les autres sont rejouables (`MERGE` par id ; `fournisseur`/`etl` : suppression des relations puis `MERGE`, le dernier traitement l'emporte ; `normalize-unite` n'écrit rien). Nuances : un rejeu de `llm-extractor` relance un appel DeepSeek payant (résultat pas forcément identique) ; `semantique-vigil` : deux réplicas sur la même caractéristique au même instant peuvent créer une ligne Milvus en double (pas Neo4j), impact faible — risque déjà présent avec les 3 conteneurs VM.
