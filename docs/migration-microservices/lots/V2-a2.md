## Préparation (05/10) — constats du DSO

- **Usage** : aucune des 5 routes n'a reçu d'appel par la gateway en 7 jours. Soit ces services sont appelés **en direct** (par un autre conteneur de la VM), soit ils ne servent plus. Question posée au LEAD avant de les basculer — les jumeaux restent UP de toute façon.
- **Code** : la VM ne fait **pas** tourner de correctif `poc` absent de `prod` (contrairement à V2-a1). C'est l'inverse pour deux services : `prod` est **plus récent** que la VM.
  - `graph-rag-api-recherche-optim` : une ligne de log ajoutée (`logging.warning("[V2-TIMING] scoring: PASS")`, commit `9fbd3407`, 17/07) — sans effet fonctionnel, coût de log négligeable.
  - `api-chat-llm` : **changement de modèle** dans `prod` (commit `f375968e`, 26/07) — `deepseek-chat` → `deepseek-v4-flash`, avec `thinking` désactivé pour garder le comportement de `deepseek-chat`. La VM tourne encore avec `deepseek-chat`. Basculer = **mettre en service ce changement** : à valider par le dev auteur (Rindra) ou le LEAD, avec un parcours de test qui compare les réponses.
- **Variables** : valeurs non secrètes identiques entre VM et Cloud Run (`NEO4J_DATABASE=neo4j`, `NEO4J_USER=neo4j`, Neo4j prod `10.0.1.218`, `LLM_PROVIDER=gemini` pour graph-rag, `ZILLIZ_URI` = `milvus-prod` pour chat-llm). Seules les adresses diffèrent, par conception (noms Docker sur la VM, enabler ou IP interne sur Cloud Run) ; chat-llm joint Qdrant par l'IP interne `10.0.1.237` au lieu de l'IP publique `34.52.142.50` de la VM. Le Rust utilise `bolt://` au lieu de `neo4j://` (même serveur, sans effet sur une instance unique).
  - ⚠️ `p0_route.sh` marque ces variables `DIFFERENT (valeur)` alors que les valeurs sont égales : son empreinte des valeurs simples n'est pas fiable (à corriger) ; la carte de valeurs de `p0_code.sh` fait foi pour le non-secret.
- **Réponses des devs (05/10 soir)** : (1) **pas d'appel direct** ; services toujours en fonction, usage **ponctuel selon les projets** (calme en ce moment) → la bascule ne déplace presque aucun trafic : le **test du dev après chaque route** est la seule preuve fonctionnelle. (2) chat-llm : « la version déployée sur la VM prime ». ⚠️ **À reconfirmer** : le commit `f375968e` est un **correctif** — d'après son message, DeepSeek a **retiré `deepseek-chat` le 24/07/2026** (API en `400`, seuls `deepseek-v4-flash` / `-pro` acceptés). La classe DeepSeek de `chat.py` sur la VM écrit `deepseek-chat` en dur : ce chemin est probablement **en échec sur la VM** depuis le 24/07, sans que personne le voie (aucun appel). Garder la version VM reviendrait à migrer une panne. Question renvoyée au dev avec ce fait. **Décision (06/10, user, sur reco DSO) : option A** — chat-llm bascule avec `deepseek-v4-flash` (correctif déjà dans `prod`, même correctif qui tourne sur GKE depuis L5) ; test du dev juste après ; on ajuste si besoin.
- **Wrappers (06/10)** : PR `chore/v2a2-wrappers-internal-ingress` — entrée `internal-and-cloud-load-balancing` sur les 5 ; **`min_instances` laissé à 0** (décision user 06/10, option A : 0 appel en 7 j, usage ponctuel ; ~50 €/mois évités ; démarrage à froid de quelques secondes accepté, à revoir si un dev s'en plaint).
- **CD (06/10)** : 4 services redéployés en entrée interne ; `graph-rag-api-recherche-rust-service` en échec de build (`uuid` 1.27.0 exige rustc 1.89, image 1.88) car le Dockerfile **ne copiait pas le `Cargo.lock` versionné** → PR `fix/graph-rag-rust-cargo-lock` (copie du lockfile, versions du 23/03, proches du binaire VM) mergée, CD vert.
- **Reste avant bascule** : wrappers au réglage cible (entrée interne, appel anonyme, `min_instances: 1`) pour les 5, chemins de santé, réponse du LEAD (usage) et décision sur le modèle de chat-llm.
