## Nature de ce lot

Ce n'est **pas** une bascule de consumers. Les quatre services B1 et `graph-rag-api-admin` sont des services HTTP : leurs jumeaux VM **continuent de servir** `api.hellopro.eu` et `mcp.hellopro.eu` jusqu'à la vague 2. Ce lot **câble les services GKE sur les données de production** (MySQL `gateway_db`, Neo4j, Elasticsearch, broker) sans arrêter la VM.

Deux décisions à prendre **avant** ce lot :

1. **`dlq-manager-service`** : le jumeau VM porte la même boucle d'auto-archivage. Deux boucles sur le même Elasticsearch prod = actions en double. **Arrêter le jumeau VM au moment du câblage**, ou ne pas câbler.
2. **Cohérence des jetons** : `ENCRYPTION_KEY`, `GOOGLE_TEMPLATES_RUNNER_ADMIN_TOKEN`, `ZOHO_GATEWAY_TOKEN` identiques entre gateway et satellites, **et** identiques à ceux du jumeau VM puisque les deux liront la même base.

Prérequis technique : créer les **Services Kubernetes** manquants pour `mcp-gateway-service` et `mcp-zoho-service`, et **jeter** la copie `gateway-mysql-shadow` (Deployment + PVC) une fois la base prod câblée.

## Analyse du code (25/09) — ce que chaque service fait seul, branché sur les données prod

Question posée : ce lot câble les copies GKE sur `gateway_db`, Neo4j, ES et le broker prod **pendant que la VM continue de servir le trafic**. Que font-elles d'elles-mêmes, sans trafic ?

| Service | Écrit au démarrage | Écrit en tâche de fond | Deux instances (VM + GKE) | Points de code |
|---|---|---|---|---|
| `api-gateway-go` | **oui** : `AutoMigrate` de 3 tables + INSERT de jetons « système » dans `info_refresh_token` pour chaque route de la carte de services | non (historique seulement par requête) | faible, mais jetons en double / lignes parasites possibles (pas d'unicité ; carte de services issue de `.env.url`, **fichier local à la VM**) | `internal/db/db.go:37-39`, `internal/db/bootstrap.go:14-38` ; défauts Docker `MYSQL_HOST=gateway-mysql`, `API_CATALOG_GRPC=api-catalog-service:9100`, `ACCOUNT_BASE_URL=http://account-service-backend:8600` ; `JWT_SECRET` identique obligatoire |
| `mcp-gateway-service` | **oui** : `AutoMigrate` de **36 tables** de `gateway_db` + UPDATE + mise à jour du statut des serveurs | **oui** : contrôle de santé toutes les 30 s → UPDATE `mcp_servers` + **alertes Slack** ; purge horaire `sso_sessions` | **élevé** : deux contrôleurs sur les mêmes lignes ; les URL stockées **en base** sont des noms Docker (`http://mcp-zoho-service:8596/mcp`…) introuvables depuis GKE → statut qui oscille et **flot d'alertes Slack** | `internal/db/mysql.go:30-90`, `internal/health/checker.go:56-162` ; `MCP_GATEWAY_PORT` défaut 8560 ≠ 8592 ; `ENCRYPTION_KEY` partagée ; icônes sur le disque VM |
| `mcp-zoho-service` | non | non (lecture seule) | aucun | `ZOHO_STUB_SERVER_ID` = UUID de la ligne prod ; `ENCRYPTION_KEY`, `ZOHO_GATEWAY_TOKEN` |
| `mcp-google-templates-runner` | non | synchro toutes les 300 s avec le gateway : reçoit les **comptes de service Google déchiffrés** et lance les processus MCP | faible pour les données, mais **secrets Google déchiffrés sur deux hôtes** | `app/gateway_sync.py:61-146` ; `MCP_GATEWAY_URL` défaut Docker |
| `graph-rag-api-admin-service` | non | non | aucun | écrit Neo4j (via le connecteur VM) **seulement sur appel HTTP** ; défauts gRPC `common_utils` = noms Docker (à poser : `15055-15058` + LLM/reranking) |
| `graph-rag-dlq-manager` | non | non | aucun sans trafic | endpoints **sans authentification** : requeue, suppression, **purge** de DLQ |
| `dlq-manager-service` | crée l'index `dlq_auto_archive_rules` | **oui** : toutes les ~60 s, applique les règles actives et passe des documents de `failed_messages_archive` en `Auto-Archived` | **élevé** ; surtout : **la copie VM est désactivée** (`profiles: ["disabled"]`, `docker-compose.yml:1257`) → câbler GKE sur ES prod **démarre** un auto-archivage qui ne tourne pas aujourd'hui | `backend/main.py:12-33`, `backend/app/es_client.py:127-171` ; endpoints sans authentification |

**Conclusion** : câbler ces services sur la prod **sans leur donner le trafic** n'apporte rien (aucun ne sert de requête tant que la VM garde `api.hellopro.eu` / `mcp.hellopro.eu`) et ajoute des risques réels : migrations de schéma de `gateway_db` lancées par une autre version de code que celle qui sert la prod, jetons parasites, alertes Slack en boucle, secrets Google dupliqués, et mise en route d'un auto-archivage ES aujourd'hui éteint.

**Recommandation (à décider CTO / LEAD)** : **ne pas jouer L7 tel que conçu le 30/09.**
- Les 4 services gateway (B1), `graph-rag-api-admin` et `graph-rag-dlq-manager` basculent **avec leur trafic** (vague 2 : DNS / reverse proxy), jumeaux VM arrêtés dans le même geste — pas avant.
- `dlq-manager-service` : ce n'est pas une migration mais **l'activation d'une fonction éteinte** ; décision métier séparée (revue écrite des règles), hors série de lots.
- Le 30/09 devient une **journée de préparation de la vague 2** : parité de version du code gateway VM ↔ image GKE (schéma), `ENCRYPTION_KEY`/`JWT_SECRET`/jetons, Services K8s manquants, réécriture des URL de `mcp_servers` (donnée prod), `.env.url`, stockage des icônes, dump `gateway_db`.
