## Ce qui bascule dans ce lot

- Les appels passant par la gateway VM pour ces 5 routes partent vers Cloud Run.
- **Écritures** : `api-ingestion` publie dans RabbitMQ (broker **prod** à câbler à la bascule, le shadow vise le broker dev) ; `api-rest-milvus` lit et peut écrire dans Milvus (prod via le connecteur VPC, recette validée) ; `prix-traitement` : à qualifier en P0.

## À savoir, service par service

| Service | Vigilance |
|---|---|
| `api-recherche` | Cœur du moteur RAG. gRPC GPU via l'enabler. Client Redis prod (vu sur Redis le 02/10 depuis la VM). Appelé aussi par `mcp-api-recherche` (V2-b) : **basculer V2-a3 avant V2-b**. |
| `api-classification` | **10 réplicas VM** derrière `api-classification-lb` : caler `max_instances` / concurrence Cloud Run sur cette capacité. Enabler 4 ports. ⚠️ `mcp-classification-produit` (VM) l'appelle → jumeau UP jusqu'à V2-b. |
| `api-rest-milvus` | ⚠️ F-HP-DEV-005 : appelle `api-recherche` via `http://localhost` → **correctif de code avant la bascule** (dev). Milvus prod via connecteur VPC `private-ranges-only` (recette validée en juillet). |
| `api-ingestion` | **Publie dans RabbitMQ** : en shadow sur le broker dev ; à la bascule, `RABBITMQ_URL` prod (valeur depuis Secret Manager, empreinte vérifiée), sinon les ingestions partent en dev sans erreur visible. Message contrôlé avec le dev. |
| `prix-traitement` | Service HTTP (port 8591) — **ne pas confondre** avec les consumers prix (L3, sur GKE). Écritures et appelants à qualifier en P0. |

## Prérequis spécifiques au lot

- P0 complet des 5 services ; **correctif `localhost` d'`api-rest-milvus` mergé** (dev).
- Câblage **prod** des écrivains (`api-ingestion` → broker prod ; `api-rest-milvus` → Milvus prod) préparé et relu, valeurs depuis Secret Manager.
- Capacité de `api-classification` calée sur les 10 réplicas VM.
- Pour les écrivains : un **message ou appel contrôlé** dont le résultat est connu, vérifié **une seule fois** (même règle qu'en vague 1).
