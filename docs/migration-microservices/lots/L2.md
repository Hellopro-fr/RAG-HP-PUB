## Incident du 21/09 — rollback à 14h57 Paris

**Ce qui s'est passé.** Bascule technique parfaite (2 min 39, 9 files reprises, 0 erreur au démarrage). À 14h32 Paris, premier
message réel sur `qc_caracterisation_queue` : chaque appel vers `api.hellopro.fr` répond `400 {"message":"Invalid format for the
given token"}`, y compris l'envoi du mail d'erreur ; le service conclut « catégorie non trouvée », publie en DLQ, ack. Dix
tentatives entre 14h32 et 14h37. La VM, sur 48 h, avait 530 réponses 200 et 0 réponse 400 sur les mêmes appels, dont cette
catégorie la veille. Rollback complet à 14h58 (1 min 31), la VM a repris.

**Cause.** Le secret K8s partagé `platform-llm-hp-secrets` portait encore les **placeholders** posés à sa création (F-HP-SEC-008) :
`hp-token` 35 caractères au lieu de 144, et une même valeur factice de 33 caractères pour `deepseek-api-key`, `gemini-api-key`,
`key-webhook`. Le pré-flight avait vérifié les **noms** de variables, pas les **valeurs**. L'IP Cloud NAT n'était pas en cause.

**Correctif (le jour même).** Les 3 clés utiles aux QC reseedées depuis Secret Manager par `kubectl patch` (empreintes SHA-256
K8s = SM = `.env` VM), puis une sonde authentifiée depuis un pod GKE sur la catégorie qui échouait : **HTTP 200**. `key-webhook`
volontairement laissée (SM ≠ VM, F-HP-SEC-023). Les 7 QC remis en shadow (broker dev, 1 réplica) avec les vraies clés.

**Ce qui change pour le rejeu.** P1 compare désormais les empreintes des variables secrètes VM vs K8s ; P0 audite tous les secrets
du namespace ; R attend la disparition des pods (`kubectl wait --for=delete`) avant `docker start` (20 s de double consommation
le 21/09). Les devs ont l'accès Logs Explorer, et la collecte des logs GKE est active depuis 14h21 (F-HP-OBS-004).

**À vérifier côté métier.** La catégorie `1002121` (10 échecs) : rejouée par la VM après rollback ? La DLQ `qc_caracterisation_queue_dlq`
est passée de 5 à 0 dans l'après-midi (drain par le dlq-manager VM probable). Le référent confirme au GO du 22/09.
